# M3 design: RMS complete

M3 adds relative and indexed files, sharing between processes, FDL,
ANALYZE/RMS_FILE, CONVERT, SORT/MERGE, and Files-11 images as devices. Its
acceptance: indexed files made on VMS open through an ODS image, survive
updates and splits, go back, and pass ANALYZE/RMS_FILE on real VMS.

## Layers

| Where | What |
| --- | --- |
| `vms-rms` (pure) | record formats (`seq`), relative files (`rel`), indexed files (`idx`), FDL (`fdl`), ANALYZE/RMS_FILE (`analyze`), on a [`Blocks`] store |
| `vmsportd` | the lock manager: `$ENQ`/`$DEQ` over the daemon's socket |
| `libvms::rms` | host RMS: a file's blocks over a host file, sharing (file locks) and record locks through the lock manager, one record stream API for all three organizations |
| `libvms` devices | `HOST:`, and ODS images mounted as devices (`MOUNT image DKA100:`) |
| utilities | CREATE (/FDL), ANALYZE/RMS_FILE, CONVERT, SORT, MERGE; TYPE, COPY, SEARCH, DIRECTORY and DCL's OPEN/READ/WRITE on every organization |
| `vms-c` | `sys$open` ... `sys$close` with `struct FAB`, `RAB`, `XABKEY`, `NAM` |

## The pure core works on blocks

```rust
/// A file's 512-byte blocks, VBN 1 first.
pub trait Blocks {
    fn read(&mut self, vbn: u32, buf: &mut [u8]) -> Result<(), Cond>;
    fn write(&mut self, vbn: u32, buf: &[u8]) -> Result<(), Cond>;
    /// Blocks allocated (VMS's HIBLK).
    fn allocated(&self) -> u32;
    /// Adds `n` zeroed blocks; returns the first new VBN.
    fn grow(&mut self, n: u32) -> Result<u32, Cond>;
}
```

`Vec<u8>` implements it for tests. The relative and indexed code reads what
it needs from `Blocks` at each call and keeps no buckets across calls, so
the host can let several processes share a file by locking around calls.

Statuses are RMS's own condition values (`vms_rms::status`, from
fixtures/rmsdef), so the host passes them on as they are.

## Files on disk

- A relative or indexed file is its VMS blocks, byte for byte, in a host
  file: VBN n is bytes `(n-1)*512 .. n*512`. Its FAB attributes (org, rfm,
  rat, mrs, bks, ...) are in the `vms.fab` extended attribute, as for
  sequential files; the prologue holds the rest.
- What VMS makes opens here unchanged, and what vmsport makes opens on VMS.
  Tests check both: files recorded on VMS (fixtures/rms, and new areas)
  are read here, and files written here go back to VMS (fixtures/vms/
  record.py) for `ANALYZE/RMS_FILE/CHECK` and DCL reads.

## Sharing and locks

- The lock manager lives in vmsportd: resources by name, the six VMS modes
  (NL, CR, CW, PR, PW, EX) and their compatibility, queueing, `NOQUEUE`,
  conversion, and release when the connection that took them closes.
- Each open of a relative or indexed file (`libvms::rms::File`) has its own
  connection, so its locks go when it closes or its process dies. Its file
  lock's mode comes from FAC and SHR: EX for no sharing, PR/PW for readers
  and writers that share reads only, CR/CW for those that share writes;
  incompatible opens get RMS$_FLK. Read-only access shares reads unless
  told otherwise, as in RMS.
- When others may change the file (it is shared and someone may write),
  each record operation runs under the file's structure lock (EX), and
  $GET/$FIND lock the record by RFA for the stream: RMS$_RLK if another
  stream holds it (the stream stays where it was), or a wait with
  RAB$V_WAT (ponytail: polled, so no wait holds the structure lock). A
  stream's next operation frees the record it held; $UPDATE and $DELETE
  free it too. The record is read again once locked.
- ponytail: one record stream per open (RAB$V_MSE's several when needed);
  sequential files take no locks and are read whole at open.
- Statuses DCL leaves, from fixtures/dclrms: OPEN %X00000001, READ
  %X00030001, READ/DELETE and WRITE/UPDATE RMS's (%X00010001), WRITE RMS's
  (OK_DUP for a repeated alternate key).

## Images as devices

`MOUNT image-file DKA100: [label] [logical]` (the image where VMS names a
drive) copies the volume's files out to a host tree in the run directory,
`mnt/DKA100/root`, each with its record attributes in `vms.fab` (relative
and indexed files whole, up to their allocation: VMS leaves the end of
file at 0 in some). `DKA100:` then names that tree, for every process of
the user: the run directory is the mount table. MOUNT defines DISK$label,
or the logical name given, concealed and terminal in the job table, and
says what VMS says (fixtures/mount). `DISMOUNT DKA100:` writes back what
changed, came or went (a changed file keeps its name, version, dates and
protection) and deassigns the name. Images are read and written with
vaxpunk's ods-image crate.

ponytail: the whole volume is copied at MOUNT and nothing goes back before
DISMOUNT; stage files as they are opened when images get big.
