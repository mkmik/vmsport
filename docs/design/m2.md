# M2 design: command tables for every program

A program in Rust or C gets its command the way a VMS image does: DCL
parses it with the verb's CLD and the program asks with `CLI$PRESENT` and
`CLI$GET_VALUE`. Run from a Unix shell, the program parses its argv with
the same table. `examples/greet` is one CLD and two programs, Rust and C,
that print the same thing (`crates/vms-examples/tests/greet.rs`).

## Rust: `libvms::cli`

Process-global, as on VMS. Run by DCL, the command is parsed already.

| Function | VMS |
| --- | --- |
| `dcl_parse(command: Option<&str>, tables: &str) -> Cond` | CLI$DCL_PARSE; `None`: DCL's command, or the table's verb and the argv |
| `present(name) -> Cond` | CLI$PRESENT |
| `get_value(name) -> Result<(String, Cond), Cond>` | CLI$GET_VALUE |
| `get_foreign(prompt) -> String` | LIB$GET_FOREIGN |
| `get_symbol(name) -> Result<(String, bool), Cond>`, `set_symbol`, `delete_symbol` | LIB$GET/SET/DELETE_SYMBOL |
| `put_output`, `getmsg`, `signal`, `stop` | LIB$PUT_OUTPUT, SYS$GETMSG, LIB$SIGNAL, LIB$STOP |
| `exit(Cond) -> !` | SYS$EXIT: the status and the symbols set go back to DCL |

A Rust program takes its table with `include_str!("FILE.CLD")`. Utilities
that want a session and files too use `libvms::image::Image`.

## C: `-lvms` and `$VMSPORT/include`

```sh
vmsport cdu GREET.CLD -o greet_tables.c      # SET COMMAND/OBJECT
cc -I $VMSPORT/include greet.c greet_tables.c -L $VMSPORT/lib -lvms -o greet
```

`crates/vms-c` builds `libvms` (cdylib and staticlib) with the routines
under their VMS names: `cli$present`, `cli$get_value`, `cli$dcl_parse`,
`lib$get_foreign`, `lib$put_output`, `lib$get_symbol`, `lib$set_symbol`,
`lib$delete_symbol`, `lib$signal`, `lib$stop`, `sys$exit`, `sys$getmsg`.
The headers are DEC C's names: `descrip.h` (`struct dsc$descriptor_s`,
`$DESCRIPTOR`), `cli$routines.h`, `lib$routines.h`, `starlet.h`, and the
status headers `ssdef.h`, `climsgdef.h`, `libdef.h`, `stsdef.h`
(`$VMS_STATUS_SUCCESS`), whose values were recorded on OpenVMS
(fixtures/cabi, `to_headers.py`).

- **Strings** are descriptors. Results go into fixed (`DSC$K_CLASS_S`,
  blank-padded, `LIB$_STRTRU` when cut) or dynamic (`DSC$K_CLASS_D`,
  resized with `realloc`) ones.
- **Tables**: a table is the CLD text. `vmsport cdu` (`Tables::to_c`) writes
  `const char MODULE[]`; `cli$dcl_parse(0, &GREET_TABLES)` passes the same
  pointer however `GREET_TABLES` is declared. A null command parses DCL's
  command or the argv; the prompt arguments are taken but not used.
- **Optional arguments**: each routine has one fixed C prototype, and a
  macro of the same name (`vms_args.h`) pads the arguments a call leaves
  out with 0: `lib$get_foreign(&line)` is `lib$get_foreign(&line, 0, 0, 0)`.
  Fixed-arity calls are the same on every ABI; Rust can't define C-variadic
  functions, and on arm64 macOS variadic calls pass arguments differently.
- **lib$signal / lib$stop** are variadic in C only: a `static inline`
  wrapper in `lib$routines.h` collects the arguments as pointer-sized words
  up to a marker the macro appends, and calls `vms$signal(stop, words, n)`.
  That reads each FAO argument as its directive in the message says: a
  number is the low 32 bits of its word (a longword, as on VMS), `!AS` a
  descriptor's address, `!AZ` a C string, `!AC` a counted one, `!AD` a
  length and characters.
- **Output order**: the library flushes C's stdio before it writes, so
  `printf` and `lib$put_output` lines keep their order.
- **Exit** with `sys$exit(status)`: a plain `return` from `main` can't
  carry a 32-bit status, and the symbols set wouldn't reach DCL.
